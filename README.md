# tsu-bot

Личный Telegram-бот для студента ТГУ (группа 932603, подгруппа «б»). Присылает расписание на сегодня, время выхода из общежития, погоду с советами по одежде, а вечером время подъёма на завтра. Есть простой список заданий.

Отвечает только владельцу (`TELEGRAM_OWNER_ID`), остальные сообщения игнорируются.

## Что делает

| Когда | Что приходит |
|---|---|
| За 60 мин до первой пары | Пары дня, время выхода, погода на выход и на конец пар, одежда |
| За 15 мин до выхода | «Выходить через 15 минут» |
| В момент выхода | «Пора выходить» |
| В 21:00 | Пары на завтра, время подъёма и выхода, прогноз |
| При изменении расписания на сегодня | Сразу: что отменено, добавлено, изменено |
| Кнопка «Что завтра?» | То же, что вечернее сообщение |
| «Добавить задание» / «Просмотреть задания» | Задания в БД в виде `Id\|title\|description`, через 7 дней удаляются |
| Сайт недоступен или формат изменился | Служебное сообщение вам |

Расписание завтра и далее просто обновляется в кэше, отдельных уведомлений об этом нет.

## Как считается время

```
выход  = начало первой очной пары − дорога − запас (5 мин)
дорога = до остановки 5 + ожидание автобуса 3 + автобус 15 + пешком от ворот до корпуса
подъём = выход − душ 10 − еда 5 − сборы 15
```

- Очной считается пара не «Онлайн». Онлайн-пары дорогу не запускают; если весь день онлайн, бот так и напишет.
- Пешком от ворот: корпус 2 это 5 мин, корпус 14 (спортзал) в конфиге стоит 4 мин **как заглушка**, поправьте под себя. Для корпуса, которого нет в списке, берётся `default_walk_from_gate_min`, и в сообщении будет пометка.
- Погода берётся на ближайший час к моменту выхода и к концу последней очной пары, одежда подбирается по худшему из двух («ощущается как»).

## Подгруппа «а»

Подгруппа задаётся одной строкой `schedule.subgroup` в `config.yaml`. Готовый пример для «а» лежит в `config.example.subgroup-a.yaml`:

```bash
cp config.example.subgroup-a.yaml config.yaml
```

Остальное (маршрут, погода, уведомления) в нём такое же. Если бот нужен и для «а», и для «б» одновременно, запускайте два экземпляра: у каждого свой токен бота (`TELEGRAM_BOT_TOKEN`), свой `config.yaml` и своя база (`DATABASE_URL`), иначе кэш расписания и задания перемешаются.

## Запуск без Docker

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env               # токен, ваш Telegram id, строка подключения к БД
cp config.example.yaml config.yaml
python -m tsu_bot
```

Таблицы создаются сами при старте. После запуска отправьте боту `/start`: появятся кнопки.

### Источник расписания

По умолчанию `source: api`: сервис ходит в JSON API InTime (`/schedule/group?id=...&dateFrom=...&dateTo=...`), формат ответа сверен с реальным. Получаются тип занятия (лекция, семинар, практика, лабораторная), преподаватель, аудитория и корпус.

Проверить источник можно без токена и БД:

```bash
python -m tsu_bot.probe
```

Если сайт изменит формат, парсер выдаст ошибку, а не мусор, и вам придёт служебное сообщение в Telegram. Править нужно будет `tsu_bot/providers/intime_api.py`.

Запасной вариант `source: ics` читает ICS-файл (путь или ссылка) и сам не обновляется. Типа занятия в нём нет.

Не встречавшиеся в ответе случаи: пара без назначенной аудитории считается очной с неизвестным корпусом, а онлайн-пара определяется по названию аудитории «Онлайн», как в ICS. Если у онлайн-пар в API другой вид, скажите, поправим.

## Запуск в Docker

В проекте есть `Dockerfile` и `docker-compose.yml` (сервисы `bot` и `db` на Postgres 16, данные в томе `pgdata`).

```bash
cp .env.example .env                 # токен, Telegram id, POSTGRES_PASSWORD
cp config.example.yaml config.yaml   # обязательно до первого запуска (см. ниже)
docker compose up -d --build
docker compose logs -f bot
```

Затем отправьте боту `/start`.

- Создайте `config.yaml` до `docker compose up`: если файла нет, Docker создаст на его месте пустую папку, и сервис не запустится. Для подгруппы «а» возьмите `config.example.subgroup-a.yaml`.
- Правка `config.yaml` или `.env` применяется командой `docker compose up -d --force-recreate bot` (образ пересобирать не нужно).
- Обновление кода: `docker compose up -d --build`.
- Пароль БД лучше из букв и цифр: он подставляется в строку подключения как есть.
- Порты наружу не открываются. Нужен только исходящий HTTPS: Telegram, Open-Meteo, InTime.
- Бот ждёт готовности БД (`depends_on` с healthcheck плюс повторные попытки подключения в самом сервисе) и перезапускается сам (`restart: unless-stopped`).
- Состояние лежит только в Postgres: задания, кэш расписания, журнал отправленных уведомлений. После перезапуска уведомления не дублируются, а пропущенную утреннюю сводку сервис отправит сразу, если выход ещё не наступил.
- Логи в stdout, ротация 10 МБ × 3 файла. Уровень задаётся `LOG_LEVEL`.
- Резервная копия заданий: `docker compose exec db pg_dump -U tsu_bot tsu_bot > backup.sql`.
- Две подгруппы одновременно: отдельная папка проекта (отдельный compose-проект) для каждой, со своим токеном бота и своим `config.yaml`.
- Тесты: `pip install -r requirements-dev.txt && pytest`. Тесты БД включаются переменной `TEST_DATABASE_URL`.

Образ собирался и запускался не в Docker, а в эквивалентной среде: проверено, что сервис стартует из набора файлов образа, читает конфиг и переменные окружения, подключается к Postgres и запускает планировщик. Сам `docker build` я проверить не мог.

## Если бот не отвечает: Telegram недоступен

В логах при этом `TelegramNetworkError: Request timeout error` на `get_me`, а расписание обновляется нормально. Сервис не падает, а повторяет подключение (10, 20, 40… до 120 секунд), планировщик работает. Но сообщения не дойдут, пока нет связи с `api.telegram.org`.

Сначала выясните, где обрыв:

```bash
# 1. С самого сервера
curl -m 10 -sS -o /dev/null -w "%{http_code}\n" https://api.telegram.org
# 2. Из контейнера (в compose-образе curl нет, поэтому Python)
docker compose run --rm --no-deps bot python -c "import urllib.request as u; print(u.urlopen('https://api.telegram.org', timeout=10).status)"
```

- Не работает ни там, ни там: доступ к Telegram режется на уровне сервера или провайдера. Нужен прокси или VPN для сервера: поднимите прокси и укажите в `.env` `TELEGRAM_PROXY=socks5://хост:порт` (или `http://хост:порт`). Прокси применяется только к Telegram, InTime и Open-Meteo идут напрямую. После правки: `docker compose up -d --force-recreate bot`.
- Работает на сервере, но не в контейнере: проблема сети Docker. Попробуйте добавить сервису `bot` в `docker-compose.yml` `dns: [1.1.1.1, 8.8.8.8]` или `network_mode: host` (тогда `db` в `DATABASE_URL` придётся заменить на `localhost` и открыть порт БД).

Токен тут ни при чём: при неверном токене ошибка другая (`Unauthorized`), а не таймаут.

## Что подкрутить под себя

`config.yaml`:

- `notify.morning_minutes_before_first_lesson`: сводка за 60 мин до пары, как вы просили. С вашими цифрами это примерно за 30 мин до выхода и за 15 до душа, поэтому реальный подъём вы узнаёте из вечернего сообщения, а утренняя сводка нужна ради погоды и списка пар. Если хотите иначе, поставьте, например, 105.
- `commute.wake_extra_min` и `commute.safety_margin_min`: мои допущения (15 и 5 мин), в ваших ответах их не было.
- `commute.walk_from_gate_min`: время пешком до других корпусов.
- `weather.latitude/longitude`: координаты центра Томска.

## Структура

```
tsu_bot/
  __main__.py        точка входа
  config.py          .env + config.yaml
  providers/         источники расписания (ics, api)
  parsing.py         разбор подгруппы, корпуса, «Онлайн»
  schedule.py        кэш в БД и поиск изменений
  commute.py         время выхода и подъёма
  weather.py         Open-Meteo
  clothing.py        правила одежды и предупреждений
  formatting.py      тексты сообщений
  notifier.py        сборка сообщений
  planner.py         расписание уведомлений (APScheduler)
  bot.py             кнопки, задания (aiogram)
  db.py              PostgreSQL
  alerts.py          служебные уведомления
  probe.py           проверка API InTime
tests/               pytest
Dockerfile, docker-compose.yml
```

## Ограничения

- Заданий нельзя удалять вручную, они исчезают через 7 дней.
- Праздники и каникулы отдельно не учитываются: если пар нет, сообщений о выходе просто нет.
- Автобус считается по средним значениям, без реального расписания и пробок.
- Гололёд определяется эвристикой по температуре и осадкам, это предупреждение, а не прогноз.
